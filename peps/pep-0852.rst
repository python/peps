Motivation
==========


The C API has no easy way to invoke asynchronous code
-----------------------------------------------------

Currently, Python's C API provides no simple interface for defining :term:`coroutine
functions <coroutine function>`. This lack of API support has not gone unnoticed by
users. For example, ``mypyc`` still `does not support all asynchronous features
<https://github.com/mypyc/mypyc/issues/868>`__ as a result of the lack of support
in CPython.

For extension developers, the current solution to this problem is to do one
of three things:

1. Don't write the asynchronous code in C, and instead define a pure-Python
   function that handles the :keyword:`await`\ s, and then call an
   event-loop-specific API from C. Given that a common use case for building
   extension modules is to improve performance, this can be a step backwards
   for developers.
2. Implement a type that implements the :term:`coroutine` protocol on its own,
   complete with all the necessary logic for a state machine. This is possible,
   but non-trivial and bad for extension maintenance; C API users should not
   have to learn about the inner workings of generators in order to use a
   built-in syntax construct.
3. Use a binding generator that has done one of the above. To `quote
   <https://github.com/python/cpython/issues/133678#issuecomment-2865557709>`__
   Petr Viktorin: "CPython should have a usable and stable C API for all
   stakeholders, and a list of a few blessed users goes against that goal."
   In other words, CPython should aim to make its C API usable (and ergonomic)
   where possible -- not encourage users to switch to binding generators.

All of these options are less than ideal, and as a result, there is support
from both Python users and core developers for adding such a C API to Python.
To `quote <https://discuss.python.org/t/42842/3>`__ Marc-André Lemburg:

    I very much do think that we need a core maintained async C API in CPython.

    We currently don’t have a way to write Python C extensions which work in
    async mode without using a shim written in Python which takes care of
    the interactions with the asyncio (and other) event loops.


A third-party library is bad for both maintainers and users
-----------------------------------------------------------

The API described in this PEP is heavily influenced by the third-party
`PyAwaitable <https://pyawaitable.zintensity.dev/>`__ library -- but why does that
need to come into CPython at all?

First and foremost, adding a dependency to a C extension typically has a very
high bar. In most cases, it's deemed safer to pick one of the solutions described
above, which each come with their own set of problems.

Second, distributing native dependencies is extremely difficult in Python's extension
ecosystem. As of recently, extension modules are increasingly being written
using C API binding libraries and not the C API itself. Unfortunately, these
binding libraries cannot wrap APIs that don't come directly from CPython, so
native libraries are effectively unusable to projects using other C API bindings.
In fact, PyAwaitable uses a vendoring technique that would make it functionally
impossible to use it from something such as PyO3.

There are have been `some <https://discuss.python.org/t/54860>`__ `discussions
<https://discuss.python.org/t/51710/>`__ about making this easier (both of whic
arised *because* PyAwaitable was so difficult to distribute), but in general, fixing
this problem seems like a much more massive proposal than what is currently being
proposed. An asynchronous C API in Python's core would be useful, and adding
one to CPython is much simpler and easier for both maintainers and users than
trying to solve a more generic problem in the packaging ecosystem; in other words,
to quote :pep:`20`, "practicality beats purity".


Why was a third-party library created in the first place?
**********************************************************

When PyAwaitable was first created in early 2024, the author of the implementation
(who is also the author of this proposal) was new to CPython contribution and
thus not in a great place to author a PEP or oversee an implementation of PyAwaitable
in CPython. A relatively simple implementation was possible without changes to
the CPython core, and as such, PyAwaitable was better fit as a library for the
time being -- though always with the intent of eventually becoming part of the
public C API.

The author has since become a core developer, and as such, it is now much more
feasible for them to maintain PyAwaitable in CPython directly.

Rationale
=========


An API for coroutine functions, not futures
-------------------------------------------

This proposal aims to add a C API for generic ``async``/``await`` constructs, *not*
an API for describing all capabilities of :mod:`asyncio`. While this PEP may
be reason for adding an ``asyncio`` C API in the future, its only goal is to
make :keyword:`async def` functions possible to implement in the C API.


Deviations from PyAwaitable
---------------------------


``PyAsync`` instead of ``PyAwaitable``
**************************************

The most obvious deviation from the original library is the use of the
``PyAsync`` prefix over ``PyAwaitable``. This is because the original
"PyAwaitable" name is a historical artifact; it was chosen as
a parallel to the ``PyCoro`` prefix, with the idea that a ``PyCoro`` was
analogous to a native ``coroutine`` object, while a ``PyAwaitable`` would
be analogous to a native ``awaitable`` object. Given that this API (and new
versions of PyAwaitable) support all of the :class:`~collections.abc.Coroutine`
protocol (in contrast to the :class:`~collections.abc.Awaitable` protocol),
this name is now misleading, and thus the rename to ``PyAsync`` felt necessary.


Simpler storage for callback values
***********************************

This API uses a single ``PyObject *`` reference and ``void *`` pointer for value
storage between callbacks instead of variadic argument lists that were stored as
arrays. PyAwaitable used the latter because it was optimized for ergonomics when
writing pure C code, but since this API is also designed to be accessible from
bindings generators (and FFIs) as well, a single pointer for each felt like the
better call. PyAwaitable's array system also turned out to be a source of
complexity and bugs, and avoiding extra complexity for CPython where possible
is ideal.

Abstract
========

This PEP describes the "pretty print protocol", a collection of changes proposed to make pretty printing more
customizable and convenient.  Classes describe the structure of their instances with a new ``__pprint__()``
method, and a printer decides how to lay that structure out.  The built-in and standard library container
types implement ``__pprint__()`` too, and a new default printer lays out every object the same way.  A new
``!p`` conversion in f-strings, t-strings and ``str.format()`` pretty prints a value, optionally with a
printer chosen by the caller.


Motivation
==========

"Pretty printing" is a feature which provides capabilities to format object representations for
better readability.  The core functionality is implemented by the standard library :mod:`pprint`
module.  ``pprint`` includes a class and APIs which users can invoke to format and print more
readable representations of objects, versus the standard ``repr()`` built-in function.  Important
use cases include pretty printing large dictionaries and other complicated objects for debugging
purposes.

Today, ``pprint`` can only lay out the types it knows about.  It keeps a private dispatch table of 25 types,
keyed on each type's ``__repr__()`` method, plus a special case for :mod:`dataclasses`.  Every other object is
printed with ``repr()`` as a single unbreakable piece of text, however much nested data it contains.  A
third-party class has no way to tell ``pprint`` about its structure, so its instances never wrap.

This PEP provides more customization and user convenience.  It is also inspired by the `Rich library's pretty
printing protocol <rich-repr-protocol_>`_.


.. _specification:

Specification
=============

There are several parts to this proposal.


``__pprint__()`` methods
------------------------

Classes can implement a new dunder method, ``__pprint__()``, which describes the pretty printed form of their
instances.  This augments ``__repr__()`` which, prior to this proposal, was the only method used to generate a
custom representation of the object.

``__pprint__()`` is optional.  If it is missing, printers fall back to the object's ``__repr__()``.
If it is defined on a class, ``__pprint__()`` takes a single argument, the object to be pretty
printed (typically ``self``), and returns an iterable, usually by being a generator.  The items it yields
form a *description stream*, which a printer interprets.

For annotations, :mod:`pprint` defines ``pprint.DescriptionType``, a type alias for the result of a
``__pprint__()`` method, defined as ``type DescriptionType = Iterable[object]``:

.. code-block:: python

    def __pprint__(self) -> pprint.DescriptionType:
        ...

Since any object can be a value in the stream, the alias does not constrain the items.  It documents what
the method returns, and gives the documentation one place to describe the stream.

An inherited ``__pprint__()`` is used only if the class that provides it comes no later in the method
resolution order than the class that provides ``__repr__()``.  So a subclass that overrides ``__repr__()``
is printed with its own ``repr()``, as it is by ``pprint`` today, unless it also provides ``__pprint__()``.
A subclass can opt back in to its base class's method with one line:

.. code-block:: python

    class D(dict):
        def __repr__(self):
            ...

        __pprint__ = dict.__pprint__

A mixin that provides ``__pprint__()`` works as expected, because in ``class C(Mixin, Base)`` the mixin
comes before ``Base`` in the method resolution order.  See :ref:`inherited-pprint` for the reasons behind
this rule.


The standard vocabulary
-----------------------

The :mod:`pprint` module defines these public names for use in a description stream.

``pprint.VALUES``, ``pprint.KWARGS`` and ``pprint.ITEMS``
    Section markers.  Each marker sets how the items that follow it are read, until the next marker.  The
    stream starts in the ``VALUES`` section.

    ============  ==========================================  ==============  ========================
    Section       Each item is                                Prints as       Mirrors
    ============  ==========================================  ==============  ========================
    ``VALUES``    Any value, tuples included                  ``value``       Positional arguments
    ``KWARGS``    ``(name, value)`` or                        ``name=value``  Keyword arguments
                  ``(name, value, default)``
    ``ITEMS``     ``(key, value)``                            ``key: value``  ``dict.items()``
    ============  ==========================================  ==============  ========================

    Under ``KWARGS``, ``name`` is a ``str`` and is printed as is.  A ``(name, value, default)`` item is
    omitted when ``value == default`` is true.  If evaluating ``bool(value == default)`` raises an
    :exc:`Exception`, the item is shown with an error placeholder in place of its value, such as
    ``arr=<error comparing to default: ValueError>``.  Under ``ITEMS``, ``key`` is pretty printed like any
    other value, so a string key gets its quotes and a container key can wrap.

``pprint.DELEGATE``
    If ``DELEGATE`` is the first item in the stream, the next item is printed in place of the object.
    :class:`collections.UserDict` uses this to print as its underlying ``dict``.

The section markers and ``DELEGATE`` are :pep:`661` :class:`sentinel` objects.

``pprint.Layout``
    Describes an object's *chrome*: the name and brackets around its items, the separator between them,
    and a few special cases.  It can also carry hints for particular printers.  A ``__pprint__()`` method
    sets the chrome of the object being printed by yielding a ``Layout`` instance as the first item in the
    stream.  Without one, the printer uses the defaults below.  The constructor takes these keyword-only
    arguments, all optional:

    * ``name``: the name used in the default brackets.  Without it, ``type(obj).__name__`` is used.
    * ``open`` and ``close``: the text before and after the items.  Without them, the object is printed as
      its name followed by the items in parentheses, or in ``({...})`` when every item is a key/value item,
      as in ``Counter({'a': 1})``.
    * ``sep``: the separator between items, ``','`` by default.  When the items fit on one line, a space
      follows each separator.
    * ``empty``: the text printed when there are no items, ``open`` followed by ``close`` by default.  For
      example, ``set`` uses ``'set()'``.
    * ``single_close``: the text used in place of ``close`` when there is exactly one item, as in the
      ``',)'`` of a one-element tuple.
    * ``recursion``: the text printed for a reference cycle back to this object, ``'...'`` by default.  For
      example, ``list`` uses ``'[...]'``, matching ``repr()``.
    * ``sortable``: whether a printer may sort the items, because their order is not significant.
      ``False`` by default.  `Nested objects`_ describes when the default printer sorts them.
    * ``hug``: whether a printer keeps the other items on the opening and closing lines when exactly one
      item is a container that does not fit, and lays out only that item on lines of its own.  ``False`` by
      default.  It affects ``Expand.FIT`` and ``Expand.ALWAYS``.  `Built-in and standard library types`_
      shows an example.
    * ``hints``: a mapping of hints for particular printers, empty by default.  By convention, each key
      names the printer that reads it, as in ``'html.role'``.  A printer ignores the keys it does not
      understand, and the default printer ignores them all.  :func:`!pprint.decompose` passes them through
      unchanged.

``pprint.Keyword`` and ``pprint.Entry``
    Small immutable classes, ``Keyword(name, value, default)`` with ``default`` optional, and
    ``Entry(key, value)``.  :func:`!pprint.decompose` returns them for keyword and key/value items.  A method
    may also yield them directly, in any section.  They are not tuples, so they are never mistaken for tuple
    values.

``pprint.BreakableString`` and ``pprint.BreakableBytes``
    Small immutable classes, ``BreakableString(value)`` and ``BreakableBytes(value)``, holding a ``str`` or
    ``bytes`` value that a printer may split across lines.  The default printer prints one as the ``repr()``
    of its value, split into adjacent literals to fit the width, as ``PrettyPrinter`` splits long strings
    and bytes today.  ``str`` and ``bytes`` describe themselves with them:

    .. code-block:: python

        class str:
            def __pprint__(self):
                yield DELEGATE
                yield BreakableString(self)

        class bytes:
            def __pprint__(self):
                yield DELEGATE
                yield BreakableBytes(self)

    Any other class that contains ``str`` or ``bytes`` values can yield these markers if it wants a
    wrappable representation.  :func:`!pprint.decompose` treats them as leaves, and a printer recognizes
    them by their type.

``pprint.FormattableNumber``
    This class takes a ``value``, similar to ``BreakableString`` and ``BreakableBytes``.  The default
    printer formats the value with its ``number_format`` option, described in `Printers`_.  The ``int`` and
    ``float`` types describe themselves with this marker, and :func:`!pprint.decompose` treats it like a
    leaf.

The default printer reads the stream permissively:

* Section markers may appear in any order, any number of times.  Items are printed in the order they are
  yielded.
* An item that does not fit its section is read as a value.  For example, a 4-tuple under ``KWARGS`` is
  printed as a tuple.
* Any object that is not part of the vocabulary is a value.  So a marker that only a user-supplied custom
  printer understands is printed as a value, usually with its ``repr()``.
* A ``Layout`` that is not the first item, and a ``DELEGATE`` that is not the first item, are values.  If
  ``DELEGATE`` is the only item, the object is printed with ``repr()``.  Items after the delegated value are
  ignored.
* The printer does not check that its output is valid Python.  For example, ``KWARGS`` items inside
  ``list``-like brackets print as ``[a=1]``.
* Exceptions raised by ``__pprint__()`` itself, or while iterating over its result, propagate, as exceptions
  raised by ``__repr__()`` do.


Leaves
------

A *leaf* is a value that the printer does not decompose any further, because its type has no usable
``__pprint__()``.  :func:`!pprint.decompose` returns ``(pprint.LEAF, None)`` for it.  The default printer
prints most leaves with ``repr()``, as one unbreakable piece of text.  The exceptions are the markers
``BreakableString``, ``BreakableBytes`` and ``FormattableNumber``, which are leaves that a printer
recognizes by their type.  The default printer splits a breakable value across lines to fit the width, and
formats a number with its ``number_format`` option.

``str``, ``bytes``, ``int`` and ``float`` are not leaves themselves.  They implement ``__pprint__()`` by
delegating to one of the above markers.  So a subclass that overrides ``__repr__()``, such as ``bool``, is
printed with its own ``repr()``, by the same rule as any other inherited ``__pprint__()``.

An ordinary object does not have to declare that it is a leaf.  The printer decomposes each value it is
given, and recursion stops on its own at leaves.


``pprint.decompose()``
----------------------

``pprint.decompose(obj)`` is a new module-level function.  It finds the usable ``__pprint__()`` method of
``type(obj)``, runs it, and normalizes one level of the stream according to the rules above.  It returns a
2-tuple ``(layout, items)``:

* ``(pprint.LEAF, None)`` if ``obj`` is a leaf.
* ``(pprint.DELEGATE, value)`` if the object delegates to ``value``.
* Otherwise, a ``Layout`` with every attribute filled in, and a list of items, each a plain value, a
  ``Keyword``, or an ``Entry``.  Keyword items equal to their defaults have been removed, and section markers
  do not appear.

So the first element always says what kind of result it is, and a caller can ``match`` on it.  A leaf's
second element is ``None`` rather than an empty sequence, so that a leaf is never mistaken for an empty
container, which returns its ``Layout`` and an empty list.

``pprint.LEAF`` is a new :pep:`661` sentinel.  It is used only in the result of ``decompose()``, and it is
not part of the stream vocabulary.  If a ``__pprint__()`` method yields it, it is printed as a value, like
any other object outside the vocabulary.  An object is a leaf when its type has no usable
``__pprint__()`` method, which includes the marker classes ``BreakableString``, ``BreakableBytes`` and
``FormattableNumber``.

``decompose()`` never recurses into the items, and it does not depend on any printer setting.  The default
printer calls it on each object it prints.  Other printers can call it to get the same reading of a stream.
A printer with its own vocabulary can call it too, and look for its own markers among the plain values,
since ``decompose()`` passes anything it does not understand through as a value.


Printers
--------

A *printer* is any callable that takes the object to print as its only argument and returns an iterable of
``str``, one for each line of output, without line endings.  A plain function can be a printer.  Code that
needs the output as a single string joins the lines with ``'\n'``, as ``!p`` does.  Nothing checks a line
for embedded newlines, so a line that contains one is joined as is.

The default printer is an instance of a new class, ``pprint.Printer``.  Its constructor takes the options of
:class:`pprint.PrettyPrinter`, except ``stream`` and ``underscore_numbers``, with the same meanings, except
for ``expand`` as described below.  Its instances are printers.

In place of ``underscore_numbers``, it takes ``number_format``, a format spec that the printer applies to
each ``FormattableNumber`` with :func:`format`.  So ``number_format='_'`` groups digits as
``underscore_numbers=True`` does, and ``number_format=','`` groups them with commas, as in
``1,234,567.125``.  If :func:`format` raises an exception for a value, the value is printed with
``repr()``.  The default, ``None``, prints every number with ``repr()``.  Any spec that the
:ref:`format specification mini-language <formatspec>` accepts can be used, so the option gains whatever
the mini-language adds later.

Three of its defaults differ from ``PrettyPrinter``'s: ``width`` is 78, ``indent`` is 4, and ``expand`` is
``Expand.FIT``.  So by default its output stays within the line length that :pep:`8` recommends, and comes
close to code formatted by tools such as `ruff`_ and `black`_.  As with ``PrettyPrinter``, ``sort_dicts``
is ``True`` by default.

The ``expand`` option takes a member of a new enumeration, ``pprint.Expand``, which says how a container
that does not fit on one line is laid out:

``Expand.NEVER``
    The items follow the open bracket and are aligned under it, as ``PrettyPrinter`` lays them out by
    default.  Nothing is indented in this layout, so ``indent`` has no effect.

``Expand.FIT``
    Each item is on its own line, indented, with a trailing separator, and the close bracket is on a line of
    its own.  Each nested container is laid out this way only if it does not fit on one line itself.  This
    is what ``PrettyPrinter``'s ``expand=True`` means.  This is the default.

``Expand.ALWAYS``
    The same layout as ``FIT``, except that once a container does not fit, every non-empty container
    inside it is laid out this way too, whether or not it fits.

In every mode, an object that fits on one line is printed on one line.

For the built-in and standard library types, the default printer's output matches ``PrettyPrinter``'s with
equivalent options, where ``Expand.NEVER`` is equivalent to ``expand=False`` with ``indent=1``, and
``Expand.FIT`` is equivalent to ``expand=True``.  The exceptions are described in `Nested objects`_, along
with these:

* Objects with a ``__pprint__()`` method wrap to fit the width.
* A reference cycle prints the ``recursion`` text of the object's ``Layout``, such as ``{...}``, at every
  level.  At the top level this replaces ``PrettyPrinter``'s ``<Recursion on dict with id=...>``.
* With ``Expand.NEVER``, the items of the ``dict`` views and the :class:`collections.abc.MappingView`
  types are aligned under the open bracket.  ``PrettyPrinter`` does not align them.
* With ``Expand.FIT`` and ``Expand.ALWAYS``, the continuation lines of a long string that is a ``dict``
  value or a keyword value are aligned under its first piece.  ``PrettyPrinter`` puts them at the
  indentation of the item instead.
* With ``Expand.NEVER``, ``indent`` has no effect.  With ``expand=False``, ``PrettyPrinter`` uses it as
  padding after each open bracket, as in ``{   'key': [   'value',``.
* An :class:`collections.OrderedDict` is printed in the form of its ``repr()``, ``OrderedDict({...})``,
  even when it does not fit on one line.  ``PrettyPrinter`` switches to a list of ``(key, value)``
  tuples, the form of ``repr()`` before Python 3.12.

``PrettyPrinter``, and the module functions such as :func:`pprint.pprint` and :func:`pprint.pformat` that
use it, are unchanged.


Nested objects
--------------

The default printer decomposes every object it prints, including each value, each keyword value, and each
key and value of a key/value item.  So nested objects wrap inside their containers at any depth, and a
``__pprint__()`` method never handles the layout of its items.  These rules apply to nested objects:

Keys
    A key is laid out like any other object, so a key with a ``__pprint__()`` method, such as a
    ``frozenset`` or ``frozendict``, can wrap.  ``PrettyPrinter`` always prints a key on one line, however
    long it is.

Values after a wrapped key
    A value normally starts on the same line as its key, after the ``': '``.  If the key wraps, the value
    starts on a new line instead, indented one level from the start of the key.  Placed after the key's last
    line, the value would start far to the right, and its own items would be pushed further.  With
    ``Expand.FIT`` and ``Expand.ALWAYS``, the last line of a wrapped key is just its closing bracket, so the
    value follows the key as usual.

Sorting
    When ``sort_dicts`` is ``True``, the items of an object whose ``Layout`` is ``sortable`` are sorted,
    key/value items by key and other items by value.  They are sorted in their natural order, as
    ``PrettyPrinter`` sorts them.  If they can't be compared with each other, or any of them is a set, they
    are sorted by their pretty printed form on one line instead.  A set's comparison operators test inclusion
    rather than order, so sorting sets in their natural order gives an arbitrary result.  The one-line form
    does not depend on hash order the way ``repr()`` does, since a set's own items are sorted too.
    ``PrettyPrinter`` instead orders each pair of items that can't be compared by their type names and
    ``id()``\ s, so its order can change from run to run.

Depth
    A key and its value are both one level deeper than their container, so ``depth`` elides deeply nested
    keys as it does values.  The limit applies however an object is laid out.  ``PrettyPrinter`` applies it
    only to objects whose elided form fits on the rest of the line.


Built-in and standard library types
-----------------------------------

These types implement ``__pprint__()``, and the default printer prints them as ``pprint`` prints them today:
``str``, ``bytes``, ``bytearray``, ``int``, ``float``, ``dict``, ``frozendict``, ``list``, ``tuple``,
``set``, ``frozenset``, the ``dict`` views, :class:`types.MappingProxyType`, :class:`types.SimpleNamespace`,
:class:`collections.OrderedDict`, :class:`collections.defaultdict`, :class:`collections.Counter`,
:class:`collections.ChainMap`, :class:`collections.deque`, :class:`collections.UserDict`,
:class:`collections.UserList`, :class:`collections.UserString`, :class:`collections.abc.MappingView`, and
:class:`string.templatelib.Template` and :class:`string.templatelib.Interpolation`.

For example, ``dict`` and ``tuple`` behave as if they were written:

.. code-block:: python

    class dict:
        def __pprint__(self):
            yield Layout(open='{', close='}', empty='{}', recursion='{...}', sortable=True)
            yield ITEMS
            yield from self.items()

    class tuple:
        def __pprint__(self):
            yield Layout(open='(', close=')', empty='()', single_close=',)', recursion='(...)')
            yield from self

``Counter`` and ``OrderedDict`` are not ``sortable``, since their order is meaningful.

The ``__pprint__()`` methods of ``defaultdict``, ``mappingproxy``, the ``MappingView`` types and ``deque``
yield a ``Layout`` with ``hug=True``, so with ``Expand.FIT`` they keep the layout that ``PrettyPrinter``
gives them with ``expand=True``:

.. code-block:: text

    defaultdict(<class 'list'>, {
        'precision': ['E', 'A', 'D', 'G'],
        'stingray': ['B', 'E', 'A', 'D', 'G'],
    })

Without ``hug``, the factory would be printed on a line of its own.  Similarly, a ``deque`` with a
``maxlen`` keeps ``], maxlen=10)`` on its closing line.

The vocabulary is defined in Python, in the ``pprint`` module.  The ``__pprint__()`` methods of types
implemented in C import the names they need from ``pprint`` the first time they are called.  Anything that
calls such a method is already pretty printing, so this adds no import that would not otherwise happen.


``dataclasses`` and named tuples
--------------------------------

When the :func:`~dataclasses.dataclass` decorator generates a ``__repr__()`` method, it also generates a
``__pprint__()`` method, which describes the same fields that ``__repr__()`` shows.  It uses the class's
``__qualname__``, as ``__repr__()`` does.  If the class body defines its own ``__repr__()``, no
``__pprint__()`` is generated, so the method resolution order rule above keeps the hand-written ``repr()`` in
use.  For ``Item(count: int, tags: list)``, the generated method is equivalent to:

.. code-block:: python

    def __pprint__(self):
        yield pprint.Layout(name=self.__class__.__qualname__)
        yield pprint.KWARGS
        yield 'count', self.count
        yield 'tags', self.tags

Classes made by :func:`collections.namedtuple` get a generated ``__pprint__()`` in the same way, so a long
named tuple wraps.


Additions to ``f-strings`` and ``str.format()``
-----------------------------------------------

In addition to the existing ``!s``, ``!r``, and ``!a`` conversion specifiers, a new ``!p`` conversion
specifier will be added.  The effect of this specifier with an expression ``value`` will be to call the
default printer (importing the ``pprint`` module as needed), passing ``value`` as the only argument, and
to join the lines it returns with ``'\n'``.  There is no trailing newline.

In f-strings, the ``!p`` conversion accepts an optional printer, given as a format spec consisting of a
single replacement field: ``f'{obj!p:{printer}}'``.  The ``printer`` expression is evaluated after ``obj``,
and its value is used directly, without being converted to a string.  The result of the f-string field is
the lines of ``printer(obj)``, joined with ``'\n'``.  :exc:`TypeError` is raised if ``printer(obj)``
returns a ``str``, which would otherwise be read as one line per character, or if any line is not a
``str``.  The ``!p`` conversion is also compatible with the ``obj=`` form, e.g. ``f'{obj=!p:{printer}}'``.

The replacement field in the format spec must have no conversion or format spec of its own.  Any other format
spec, such as ``f'{obj!p:>40}'``, is a :exc:`SyntaxError`, since its shape is known at compile time.  An
empty spec, as in ``f'{obj!p:}'``, is the same as no spec.  There is no need for padding or alignment specs,
since a printer can provide them.

In ``str.format()``, a format spec after ``!p`` is applied to the pretty printed string, as it is after
``!s``, ``!r`` and ``!a``.  So ``'{!p:>40}'.format(obj)`` pads the result.  A printer cannot be passed this
way, since ``str.format()`` converts a nested replacement field to a string before it applies the spec.
See :ref:`Deferred Ideas <deferred>`.


T-strings
---------

The ``!p`` conversion is also allowed in t-strings.  As with the other conversions, it is not applied when
the template is created.  The :class:`~string.templatelib.Interpolation` records it, and the code that
processes the template decides what to do with it:

* :attr:`!Interpolation.conversion` is ``'p'``.
* A printer given in the format spec, as in ``t'{obj!p:{printer}}'``, is evaluated when the template is
  created, and kept without being converted to a string, in a new attribute, :attr:`!Interpolation.printer`.
  It is ``None`` when no printer is given.  :attr:`!Interpolation.format_spec` is the empty string.
* The format spec follows the same rules as in f-strings.  It must be empty or a single plain replacement
  field, and anything else is a :exc:`SyntaxError`.
* The :class:`!Interpolation` constructor takes a new optional ``printer`` argument, which is accepted only
  with the ``'p'`` conversion.  ``printer`` is added to ``__match_args__``, and appears in the ``repr()``
  when it is set.
* :func:`string.templatelib.convert` handles ``'p'``, and takes a new optional ``printer`` argument.
  ``convert(obj, 'p', printer)`` returns what ``f'{obj!p:{printer}}'`` would, and ``convert(obj, 'p')``
  uses the default printer.

For example:

.. code-block:: pycon
   :force:

    >>> from string.templatelib import convert
    >>> basses = ['precision', 'jazz', 'stingray']
    >>> printer = pprint.Printer(width=20)
    >>> interpolation = t'{basses!p:{printer}}'.interpolations[0]
    >>> interpolation.conversion, interpolation.printer is printer
    ('p', True)
    >>> print(convert(interpolation.value, interpolation.conversion, interpolation.printer))
    [
        'precision',
        'jazz',
        'stingray',
    ]


Additions to the C-API
----------------------

To support ``!p``, a new function, ``PyObject_Pretty()``, is added to the
`Limited C API <https://docs.python.org/3/c-api/stable.html#limited-c-api>`_.
This function takes two arguments: a ``PyObject *`` for the object to pretty
print, and an optional ``PyObject *`` for the printer (which may be ``NULL``).
When the printer is ``NULL``, this function calls the default printer with the
object as its argument.  When the printer is not ``NULL``, this function calls
the printer with the object as its argument.  Either way, it joins the lines
that the printer returns with ``'\n'`` and returns the resulting ``str``,
raising :exc:`TypeError` in the same cases as ``!p``.

Returning a ``str`` mirrors :c:func:`PyObject_Str`, :c:func:`PyObject_Repr` and
:c:func:`PyObject_ASCII`, the functions behind ``!s``, ``!r`` and ``!a``.  Both
f-strings and ``str.format()`` need the joined string, so the join and its
checks live in one place.  C code that wants the lines calls the printer
directly.


Rationale
=========

Pretty printing is very useful for displaying complex data structures, like dictionaries read from JSON
content.  By providing a way for classes to describe how their instances participate in pretty printing,
users have more options for visually improving the display of their complex data, especially for debugging.

By adding a ``!p`` conversion specifier to f-strings and ``str.format()``, debugging with user-friendly
display is made even more convenient.  Since no extra imports are required, users can easily just piggyback
on well-worn "print debugging" patterns, at least for the most common use cases.

These extensions work both independently and complementarily, to provide powerful new use cases.


Description, not layout
-----------------------

A ``__pprint__()`` method describes *what* an object contains: its positional values, its keyword
arguments, or its key/value items, along with the brackets and name that surround them.  It does not decide
*where* the line breaks go.  The printer makes every layout decision, so width, indentation, depth and
sorting work the same way for every object, and a nested object wraps correctly inside its container
without knowing anything about the container.  This also means a ``__pprint__()`` method never needs the
printer's state passed to it.

Because the built-in containers describe themselves with the same protocol, the default printer has one
layout algorithm for everything it prints.  The reference implementation uses a `Wadler-style document
algebra <wadler-prettier_>`_ with `Oppen-style bounded lookahead <oppen-prettyprinting_>`_, but the
protocol does not depend on that choice.


A new default printer
---------------------

This PEP adds a new default printer and leaves :class:`pprint.PrettyPrinter` unchanged.  The new layout
algorithm is different enough from ``PrettyPrinter``'s that one class cannot keep its existing output and
overridable hooks working while also providing the new behavior.

``PrettyPrinter`` also chooses a layout by looking each object's type up in a hard-coded dispatch table.  The
new printer has no table of types.  Every object, including the built-in containers, describes itself through
``__pprint__()``, so a user-defined class takes part in exactly the same way that ``list`` and ``dict`` do.

Existing code that uses ``PrettyPrinter`` keeps its exact output, and code that wants the protocol opts in by
using the new printer.


Sections, not guessing
----------------------

The protocol is based on `Rich's <rich-repr-protocol_>`_, which reads each yielded tuple by its shape: a
2-tuple is a keyword argument and a 3-tuple is a keyword argument with a default.  This PEP replaces that
guessing with explicit *section markers*, ``pprint.VALUES``, ``pprint.KWARGS`` and ``pprint.ITEMS``, which
say how the plain tuples that follow them are read.  A positional tuple value needs no special spelling, and
a positional ``('a', 1, 2)`` can no longer print silently as ``a=1``.  Items remain plain tuples, so a method
still needs no classes.


A stream that printers interpret
--------------------------------

A ``__pprint__()`` method yields a stream of items that a printer interprets.  This PEP defines a standard
vocabulary for the default printer.  A user can also write a printer with a custom vocabulary, and give
their classes ``__pprint__()`` methods that yield it, while the default printer can still print the same
objects.

That is why the default printer is deliberately permissive.  It does not enforce an order of markers, and it
prints an item it does not recognize as a value, usually with ``repr()``, rather than raising an exception.
Pretty printing is mostly used for debugging, where output that shows a description is more helpful than an
exception about its shape.


Printers return lines
---------------------

A printer returns the lines of its output rather than one string.  Code that works line by line, such as
code that indents or prefixes each line for a log record or a doctest, then does not have to split the
output again.  A printer that produces its lines lazily lets a caller print them immediately, preserving the
ability to stop at any point.  Joining the lines is left to the code that needs a single string, such as
``!p``.


.. _inherited-pprint:

Inherited ``__pprint__()`` methods
----------------------------------

An inherited ``__pprint__()`` is used only if its class comes no later in the method resolution order than
the class that provides ``__repr__()``.

This matches ``pprint`` today, which looks up its layout function by ``type(obj).__repr__``.  So
``class D(dict): pass`` is pretty printed as a ``dict``, but a ``dict`` subclass that overrides
``__repr__()`` is printed with its own ``repr()``.  Once the built-in containers implement ``__pprint__()``,
plain inheritance would change that for every such subclass.

More importantly, a description has to agree with ``repr()``.  A subclass that changes its ``repr()`` may
add fields, change its name or leave items out, and the ``__pprint__()`` method it inherits knows nothing
about that.  The result would be misleading in a tool used for debugging.  Worse, it could print what
``repr()`` hides, such as the values of secret keys.  See `Security Implications`_.

Opting back in takes one line, as shown in the specification, and a mixin that provides ``__pprint__()``
needs none.  The same rule keeps a hand-written ``__repr__()`` in use for a class decorated with
:func:`~dataclasses.dataclass`.


.. _examples:

Examples
========

A custom ``__pprint__()`` method can be used to customize the representation of the object, such as with this
class:

.. code-block:: python

    import pprint

    class Bass:
        def __init__(self, strings: int, pickups: str, active: bool=False):
            self._strings = strings
            self._pickups = pickups
            self._active = active

        def __pprint__(self):
            yield self._strings
            yield pprint.KWARGS
            yield 'pickups', self._pickups
            yield 'active', self._active, False

Now let's create a couple of instances and pretty print them:

.. code-block:: pycon
   :force:

    >>> precision = Bass(4, 'split coil P', active=False)
    >>> stingray = Bass(5, 'humbucker', active=True)

    >>> print(f'{precision!p}')
    Bass(4, pickups='split coil P')
    >>> print(f'{stingray=!p}')
    stingray=Bass(5, pickups='humbucker', active=True)

    >>> print('{!p}'.format(precision))
    Bass(4, pickups='split coil P')

For more complex objects, ``!p`` can help make debugging output more readable:

.. code-block:: pycon
   :force:

    >>> import os
    >>> print(os.pathconf_names)

    >>> print(f'{os.pathconf_names = !p}')
    os.pathconf_names = {
        'PC_ALLOC_SIZE_MIN': 16,
        'PC_ASYNC_IO': 17,
        'PC_CHOWN_RESTRICTED': 7,
        'PC_FILESIZEBITS': 18,
        'PC_LINK_MAX': 1,
        'PC_MAX_CANON': 2,
        'PC_MAX_INPUT': 3,
        'PC_MIN_HOLE_SIZE': 27,
        'PC_NAME_MAX': 4,
        'PC_NO_TRUNC': 8,
        'PC_PATH_MAX': 5,

In f-strings, the ``!p`` conversion specifier also accepts a printer, such as a ``pprint.Printer`` with its
own options:

.. code-block:: pycon
   :force:

    >>> narrow = pprint.Printer(width=30)
    >>> print(f'{stingray!p:{narrow}}')
    Bass(
        5,
        pickups='humbucker',
        active=True,
    )

    >>> hanging = pprint.Printer(width=30, expand=pprint.Expand.NEVER)
    >>> print(f'{stingray!p:{hanging}}')
    Bass(5,
         pickups='humbucker',
         active=True)

A printer can also be a plain function that takes the object and returns its lines:

.. code-block:: pycon
   :force:

    >>> def slappa(da: Bass) -> Iterator[str]:
    ...     yield 'All about that bass'

    >>> print(f'{precision=!p:{slappa}}')
    precision=All about that bass

Since tuples are read according to the current section, a positional tuple value needs nothing special:

.. code-block:: pycon
   :force:

    >>> class Things:
    ...     def __pprint__(self):
    ...         yield (1, 2)
    ...         yield (3, 4)
    ...         yield pprint.KWARGS
    ...         yield 'arg', (5, 6)
    ...
    >>> print(f'{Things()!p}')
    Things((1, 2), (3, 4), arg=(5, 6))

Objects with a ``__pprint__()`` method wrap, however deeply they are nested:

.. code-block:: python

    class Node:
        def __init__(self, name, children=None):
            self.name = name
            self.children = [] if children is None else children

        def __pprint__(self):
            yield self.name
            yield pprint.KWARGS
            yield 'children', self.children, []

.. code-block:: pycon
   :force:

    >>> tree = Node('root', [Node('left', [Node('leaf')]), Node('right')])
    >>> print(f'{tree!p:{pprint.Printer(width=60)}}')
    Node(
        'root',
        children=[
            Node('left', children=[Node('leaf')]),
            Node('right'),
        ],
    )

A ``Layout`` changes the brackets.  This class prints in the angular form that Rich supports:

.. code-block:: python

    class Note:
        def __init__(self, pitch, beats=1):
            self.pitch = pitch
            self.beats = beats

        def __pprint__(self):
            yield pprint.Layout(open='<Note ', close='>', sep='')
            yield pprint.KWARGS
            yield 'pitch', self.pitch
            yield 'beats', self.beats, 1

.. code-block:: pycon
   :force:

    >>> print(f"{Note('E', beats=2)!p}")
    <Note pitch='E' beats=2>
    >>> print(f"{Note('A')!p}")
    <Note pitch='A'>

A hint asks a particular printer for a different presentation, without changing what other printers print.
This class asks an HTML printer to show it as a table, with ``<th>`` cells for the headers and a ``<tr>``
for each row:

.. code-block:: python

    @dataclass
    class Table:
        headers: list[str]
        rows: list[list[object]]

        def __pprint__(self):
            yield pprint.Layout(hints={'html.role': 'table'})
            yield pprint.KWARGS
            yield 'headers', self.headers
            yield 'rows', self.rows

The default printer ignores the hint, so its output still agrees with ``repr()``:

.. code-block:: pycon
   :force:

    >>> print(f"{Table(['Bass', 'Strings'], [['Precision', 4], ['Stingray', 5]])!p}")
    Table(headers=['Bass', 'Strings'], rows=[['Precision', 4], ['Stingray', 5]])

The class writes its own ``__pprint__()``, since the method that :mod:`dataclasses` generates has no way to
add a hint.

``DELEGATE`` prints another object in place of this one.  :class:`collections.UserDict` is equivalent to:

.. code-block:: python

    class UserDict:
        def __pprint__(self):
            yield pprint.DELEGATE
            yield self.data

A library that defines its own printer can also mark values for it.  A wrapper class that delegates to the
value it wraps degrades gracefully when it reaches a printer that doesn't know about it:

.. code-block:: python

    class Emphasis:
        def __init__(self, value):
            self.value = value

        def __pprint__(self):
            # Printers that don't understand emphasis show the plain value.
            yield pprint.DELEGATE
            yield self.value

.. code-block:: pycon
   :force:

    >>> notes = [Note('E'), Emphasis(Note('A')), Note('D')]
    >>> print(f'{notes!p}')
    [<Note pitch='E'>, <Note pitch='A'>, <Note pitch='D'>]

The default printer prints the wrapped value in place of the wrapper.  A printer that understands
``Emphasis`` recognizes it among the list's items returned by ``pprint.decompose()``, and shows the wrapped
value emphasized.  A marker yielded in the list's stream instead would appear in the default printer's
output as a value.  Unlike a ``Layout`` hint, which describes an object's own presentation, the wrapper
marks a value inside another object.


Backwards Compatibility
=======================

This PEP adds new APIs and leaves :class:`pprint.PrettyPrinter` and the existing ``pprint`` functions
unchanged, so existing code is not affected.


Other pretty printing protocols
-------------------------------

Several third-party libraries have their own pretty printing protocols.  This PEP's protocol is not
compatible with them out of the box, but an object that supports one of them can add a ``__pprint__()``
method that adapts to this PEP's protocol, usually in a few lines.  A library can also teach its own printer
to read ``__pprint__()`` descriptions by calling ``pprint.decompose()``, which saves it from reimplementing
the rules of the stream.

`Rich <rich-repr-protocol_>`_
    Rich's ``__rich_repr__()`` method reads each yielded item by its shape: a plain value is positional, and a
    tuple starting with a name is a keyword argument, optionally with a default.  Since this PEP reads tuples
    by section, a ``__rich_repr__()`` method cannot be used unchanged as a ``__pprint__()`` method, but it can
    be adapted:

    .. code-block:: python

        class Bird:
            def __rich_repr__(self):
                yield self.name
                yield 'eggs', self.eggs
                yield 'fly', self.fly, True

            def __pprint__(self):
                # Each Rich item says how it is meant, so switch sections to match.
                for item in self.__rich_repr__():
                    match item:
                        case (str(), _) | (str(), _, _):
                            yield pprint.KWARGS
                        case _:
                            yield pprint.VALUES
                    yield item

    Rich could provide such an adapter as a mixin or a decorator.  Rich's angular form, ``<Name a=1>``, can be
    expressed with a ``Layout``, as in the ``Note`` example above.

IPython
    IPython's ``_repr_pretty_(self, p, cycle)`` method drives IPython's printer directly, rather than
    describing the object.  An object with a ``_repr_pretty_()`` method can add a ``__pprint__()`` method for
    other printers, and IPython's printer could print objects that have only a ``__pprint__()`` method by
    calling ``pprint.decompose()``.

Code generators
    Libraries that generate ``__repr__()`` methods, such as `attrs`_, can generate ``__pprint__()`` methods
    the same way :mod:`dataclasses` does.


Security Implications
=====================

A class may write a ``repr()`` that hides information, such as the values of secret keys in a mapping.  If
the class inherits ``__pprint__()`` from a base class that yields every item, a printer would show what the
``repr()`` hides.  The rule for :ref:`inherited __pprint__() methods <inherited-pprint>` prevents this, since
a class that overrides ``__repr__()`` is printed with that ``repr()`` unless it also provides or opts in to a
``__pprint__()`` method.  A class that does provide one is responsible for keeping it consistent with its
``repr()``.

There are no other known security implications for this proposal.


How to Teach This
=================

Documentation and examples are added to the ``pprint`` module, f-strings, t-strings, and
``str.format()``.
Beginners don't need to be taught these new features until they want prettier representations of
their objects.

Most classes need only plain values, ``pprint.KWARGS``, and ``(name, value)`` or ``(name, value, default)``
tuples, as in the ``Bass`` example.  ``Layout``, ``ITEMS`` and ``DELEGATE`` can be taught when a class wants
different brackets, holds key/value data, or wraps another object.  Authors of printers are pointed to
``pprint.decompose()``.


Reference Implementation
========================

A reference implementation is in progress on a `PEP author branch of the CPython main branch
<https://github.com/ericvsmith/cpython/tree/PEP-813-pprint>`__.


Rejected Ideas
==============

Return types other than plain tuples
------------------------------------

We considered an alternative :ref:`specification <specification>` of the ``__pprint__()`` return
values, where either :func:`~collections.namedtuple`\s, :mod:`dataclasses`, or a duck-typed instance
were used as the return types.  Ultimately we rejected this because we don't want to force folks to
define a new class just to return values from this function.  ``Keyword`` and ``Entry`` may be yielded,
but plain tuples are always enough.

Section markers as ``Layout`` subclasses
----------------------------------------

We considered making ``KWARGS`` and ``ITEMS`` subclasses of ``Layout``, so that one item could set both the
chrome and the first section.  Sections can change in the middle of a stream, so the plain markers would
still be needed, and a section is not a kind of chrome.  It would not help annotations either, since any
object can be a value.

Reading tuples by their shape
-----------------------------

The earlier version of this PEP followed Rich's protocol and read a 2-tuple as a keyword argument and a
3-tuple as a keyword argument with a default, whatever their contents.  A positional value that happened to
be a tuple could not be yielded as is, and had to be wrapped as ``(None, value)``.  Forgetting the wrapper
raised no error, and the value was printed as something else.  A positional ``('a', 1, 2)`` came out as
``a=1``, and a positional ``('a', 1, 1)`` disappeared, because its "value" equaled its "default".  See
`Sections, not guessing`_.

Requiring an order of sections
------------------------------

We considered requiring ``VALUES`` before ``KWARGS``, as in a call, with ``ITEMS`` standing alone, and raising
:exc:`TypeError` when these were given out of order.  We rejected this in favor of a permissive printer, so
that other printers can interpret the stream according to their own rules, and so that debugging output
never fails because of the shape of a description stream.

Passing layout state to ``__pprint__()``
----------------------------------------

We considered passing the width, indentation, current column and nesting level to ``__pprint__()``, so that
an object could lay itself out.  Every class would then need to reimplement layout, and nested objects would
need to cooperate with their containers.  A description-only protocol keeps all layout in the printer.

Plain inheritance of ``__pprint__()``
-------------------------------------

We considered letting ``__pprint__()`` be inherited like any other method.  Once the built-in types
implement it, every subclass of them that overrides ``__repr__()`` would print differently under the new
printer than it does today, with output that may disagree with its ``repr()``, or show what its ``repr()``
hides.  See :ref:`inherited-pprint`.

Only a ``__pprint__()`` defined on the object's own class
---------------------------------------------------------

We considered using ``__pprint__()`` only when it is defined on ``type(obj)`` itself.  Then
``class D(dict): pass`` would no longer be pretty printed as a ``dict``, which ``pprint`` does today, and a
mixin that provides ``__pprint__()`` would not work.

Rebuilding ``PrettyPrinter``
----------------------------

We considered reimplementing :class:`pprint.PrettyPrinter` on top of the protocol, replacing its dispatch
table.  Its public ``format()`` method and its dispatch functions are hooks that subclasses can override,
and none of them fit a description-only design.  Keeping them compatible while making the protocol work would
mean maintaining two layout engines in one class.  See `A new default printer`_.

Keys on one line
----------------

We considered keeping ``PrettyPrinter``'s rule that a key is never wrapped, however long it is.  A key can be
a container, such as a ``frozenset``, so it can be as long as any value.  Printed on one line, a long key
runs past the width, and its value, which starts after the key, is pushed even further to the right.  See
`Nested objects`_.

A ``pformat()`` method on printers
----------------------------------

We considered requiring a printer to be an object with a ``pformat()`` method, so that ``PrettyPrinter``
instances would be printers as is.  Since the default printer is new, a plain callable is simpler, and a
function can be a printer.

Handling strings and integers natively
--------------------------------------

We considered having the printer recognize ``str``, ``bytes`` and ``int`` and handle them itself, as
``PrettyPrinter`` does.  ``BreakableString``, ``BreakableBytes`` and ``FormattableNumber`` make that
handling available to any class, and let these types follow the same rules as every other type, including
the rule for inherited methods.  The cost is a ``__pprint__()`` call for each string and integer printed,
which are the most common values in large structures.

A ``Delegate(obj)`` wrapper
---------------------------

We considered a class wrapping the delegated object, yielded first in place of a ``Layout``.  A
``DELEGATE`` sentinel followed by the value keeps ``Layout`` as the only class with a special meaning at
the start of a stream, and makes delegation one more sentinel alongside the section markers.  Printers
and :func:`!pprint.decompose` then read every stream the same way.  It also avoids allocating a wrapper on
each call, a minor optimization.

Format specs for padding and alignment
--------------------------------------

Supporting specs like ``f'{obj!p:>40}'`` would mean choosing between a printer and a string format spec.  A
printer can pad and align its own output, as in ``f'{obj!p:{MyPrinter(padding=40)}}'``.


.. _deferred:

Deferred Ideas
==============

#. A printer format spec for ``!p`` conversions in ``str.format()``.

#. An ``Expand.EXPLODE`` member.  It would lay out every non-empty container as ``FIT`` does when a
   container does not fit, even when the whole object fits on one line, the same way `ruff`_ and `black`_
   keep a collection exploded when it ends with a trailing comma (which a printer, working on objects rather
   than source, can't see).

#. Printing the instance attributes of classes that use the default ``object.__repr__()``.  Such a class
   prints as ``<Point object at 0x...>`` today.  A ``__pprint__()`` method could instead yield its instance
   attributes under ``KWARGS``, so that it prints as ``Point(x=1, y=2)``, the way
   :class:`types.SimpleNamespace` does.

   The first step would be an opt-in, such as a mixin, a decorator, or a helper assigned as
   ``__pprint__ = pprint.from_attributes`` (the name is illustrative only).  The author of the class then
   decides whether its attributes are safe to show.

   A default ``object.__pprint__()`` could be added later, once there is experience with the opt-in.  The
   rule for :ref:`inherited __pprint__() methods <inherited-pprint>` already limits it to classes that do
   not override ``__repr__()``, since ``object`` comes last in every method resolution order.  It could
   potentially reveal attributes that the default ``repr()`` hides, such as a password or token stored on an
   instance, in logs and other debugging output, so `Security Implications`_ would have to be revisited.  It
   would also be a deliberate exception to the principle that a description agrees with ``repr()``.  And it
   would need rules for ``__slots__`` classes without a ``__dict__``, for attributes whose names start with
   an underscore, for computed attributes such as those of :func:`functools.cached_property`, and for large
   object graphs.

#. A table of markers in the default printer.  The default printer handles a fixed set of markers:
   ``BreakableString``, ``BreakableBytes`` and ``FormattableNumber``.  ``Printer`` could instead
   take a table that maps a marker class to a function that renders it, with the built-in markers as
   its default entries.  A user could then replace the built-in markers as well as add new ones,
   without subclassing ``Printer``.  For example, a class could yield its timestamp wrapped in a
   marker of its own, and a printer could show it in a chosen format:

   .. code-block:: python

       @dataclass(frozen=True)
       class Timestamp:
           value: datetime

       class Event:
           def __pprint__(self):
               yield pprint.KWARGS
               yield 'name', self.name
               yield 'when', Timestamp(self.when)

       def format_timestamp(marker, *, width, last_width, top_level):
           yield marker.value.strftime('%Y-%m-%d %H:%M')

       printer = pprint.Printer(markers={Timestamp: format_timestamp})

   The names are illustrative only.  A function takes the marker and returns an iterable of lines.
   ``width`` is the room for each line, from the column where the marker starts, and ``last_width`` is the
   room for the last line, which leaves space for any text that follows it on the same line.
   ``top_level`` is true when the marker is the whole object being printed.  The printer places the first
   line at the current position, and the rest at the marker's starting column.  The widths let a function
   split its value to fit, as the default printer splits strings, and ``top_level`` lets it parenthesize
   them.  Called with an unlimited width, a function returns the one-line form that the printer uses to
   decide whether a container fits.

   A printer would check its table for each object before calling :func:`!pprint.decompose`, so any class
   can be a marker, including a dataclass like ``Timestamp``, which has a generated ``__pprint__()``.  A
   printer whose table has no entry for a marker prints it like any other object, with its ``__pprint__()``
   if it has one and with ``repr()`` otherwise.  :func:`!pprint.decompose` itself does not depend on any
   printer, so it does not know about markers.

   The reference implementation already renders the built-in markers this way, through a table that is
   not yet public.

   This would go well with a way to change the default printer that ``!p`` uses, so that a configured
   printer reaches plain ``f'{obj!p}'``.  A process-wide setting, such as ``pprint.set_default_printer()``,
   could be paired with a context manager that changes it temporarily.  Backing both with a
   :mod:`contextvars` variable would keep threads and asynchronous tasks from seeing each other's printer.


Open Issues
===========

* Names.  ``Layout`` for the description of an object's chrome, ``pprint.DescriptionType`` for the
  annotation of a ``__pprint__()`` result, ``pprint.Printer`` for the default printer, and ``hug`` for the
  ``Layout`` attribute are working names.
* The exact rule for ``hug``, which the reference implementation will settle.
* Where the new code lives.  The authors lean toward implementing the printer in Python, in ``pprint``.
  Pretty printing is mostly used for debugging, so the maintainability of the printer matters more than the
  performance costs of using it.  Those costs are the import of a Python module the first time ``!p`` is
  used, and the slower execution of Python code compared with C.
* Whether ``__pprint__()`` should take a context argument from the printer.  As specified, it takes only
  ``self``, and the printer detects reference cycles and prints the ``recursion`` text of the object's
  ``Layout``.  A context would move recursion handling into the objects, much as
  :func:`reprlib.recursive_repr` does for ``__repr__()``, at the cost of making every ``__pprint__()`` method
  more complicated.  A context would not carry layout state.  See `Passing layout state to __pprint__()`_.
* Whether :func:`pprint.pprint` and :func:`pprint.pformat` should eventually use the new default printer.
* A helper that runs a base class's ``__pprint__()`` and drops its ``Layout``, so a subclass can change the
  brackets and keep the items.  The obvious name, ``pprint.items()``, is easily confused with the ``ITEMS``
  marker, since the helper returns all of the stream's items, not only key/value items.
* Whether the method resolution order rule for ``__pprint__()`` and ``__repr__()`` is the right one.
* Whether a generated dataclass ``__pprint__()`` should hide fields equal to their defaults.  Since
  ``repr()`` shows every field, for now it does not.
* How a class can add ``hints`` to the ``__pprint__()`` method that :mod:`dataclasses` generates.  A
  ``dataclass`` option, such as ``pprint_hints=``, could supply them.  So could a helper that runs the
  generated method and replaces its ``Layout``, like the helper for base classes above.
* Whether the interactive interpreter should display an object in its pretty printed form, rather than with
  its ``repr()``, when its type has a usable ``__pprint__()``.  Since the built-in containers implement
  ``__pprint__()``, this would change how the REPL displays most results.  The authors think it would be
  very handy, but it has a cost.  Pretty printed output depends on the printer's layout algorithm and on the
  width of the terminal, and either can change, so REPL output could no longer be pasted into a doctest that
  works across Python versions.  Turning it on by default would therefore need a way to turn it off, such as
  a ``-X pretty=0`` option with a matching ``PYTHON_PRETTY`` environment variable, and a :data:`sys.flags`
  entry that reports it.

  One way to do this is for the REPL to install a pretty printing :func:`sys.displayhook` at startup, unless
  the option turns it off.  :data:`sys.__displayhook__` would keep using ``repr()``, so a session could
  switch back at any time with ``sys.displayhook = sys.__displayhook__``.  :mod:`doctest` already runs
  examples with ``sys.__displayhook__``, so doctests themselves would be unaffected.
* Whether the ``print()`` built-in function should take a ``pretty`` argument, as an earlier draft of this
  PEP proposed.  The ``!p`` conversion covers most of its uses, so the authors lean against it, but it may
  help with pretty printed REPL output, described above.
* Whether :func:`!pprint.decompose` should set the default chrome attributes in the ``Layout`` it returns.
  As specified, it returns a ``Layout`` with every attribute set, so a printer cannot tell chrome that an
  object chose from the defaults.  For example, ``list`` chooses ``open='['`` and ``close=']'``, while
  ``Bass``, which yields no ``Layout``, gets the defaults ``open='Bass('`` and ``close=')'``.  A printer for
  another format, such as HTML, may want to keep the chrome an object chose but replace the defaults with its
  own, for example by showing the name as a heading.  :func:`!pprint.decompose` could instead leave the
  attributes that an object did not set as ``None``, and let each printer supply its own defaults.
* Sorting for other printers.  The rules for sorting described in `Nested objects`_ live in the default
  printer, so every other printer that honors ``sortable`` has to reimplement them.  :mod:`pprint` could
  provide a public helper for sorting items, or ``sortable`` could be advisory, with each printer free to
  sort as it likes.

Change History
==============

* `[DD-Mmm-2026] <https://discuss.python.org/t/pep-813-the-pretty-print-protocol/106242/[NNN]>`__

  * ``__pprint__()`` describes an object's structure, and the printer makes all layout decisions.
  * Section markers ``pprint.VALUES``, ``pprint.KWARGS`` and ``pprint.ITEMS`` say how tuples are read,
    replacing the reading of tuples by their shape and the "false-y" name for positional tuple values.
  * Add ``pprint.Layout`` for an object's chrome, the ``pprint.DELEGATE`` marker, and the
    ``pprint.Keyword`` and ``pprint.Entry`` types.  The markers are :pep:`661` sentinels.
  * Specify that the default printer reads the stream permissively, and that other printers may define their
    own vocabulary.
  * Add ``pprint.decompose()``, and the ``pprint.LEAF`` sentinel that it returns for a leaf.
  * Defer a table of markers in the default printer, and a way to change the default printer.
  * Add ``pprint.DescriptionType`` for annotating ``__pprint__()`` methods.
  * Add a ``hints`` attribute to ``pprint.Layout``, for particular printers.
  * Add a ``hug`` attribute to ``pprint.Layout``, so that ``defaultdict`` and similar types keep
    ``PrettyPrinter``'s layout.
  * Add a new default printer, ``pprint.Printer``, and leave ``pprint.PrettyPrinter`` unchanged.
  * A printer returns an iterable of lines, and ``!p`` joins them with ``'\n'``.
  * Specify how the default printer lays out, sorts and limits the depth of nested objects, including keys
    that wrap.
  * The default printer's ``expand`` option takes a ``pprint.Expand`` member: ``NEVER``, ``FIT`` or
    ``ALWAYS``.  Its defaults are ``width=78``, ``indent=4`` and ``expand=Expand.FIT``.
  * The built-in and standard library container types implement ``__pprint__()``.  ``str`` and ``bytes``
    describe themselves with the new ``pprint.BreakableString`` and ``pprint.BreakableBytes``, and ``int``
    and ``float`` with the new ``pprint.FormattableNumber``, so the printer handles no type natively.
  * The default printer's ``number_format`` option replaces ``underscore_numbers``.
  * Specify when an inherited ``__pprint__()`` is used, and explain why.
  * :mod:`dataclasses` and :func:`~collections.namedtuple` generate ``__pprint__()`` methods.
  * The ``!p`` format spec is a single replacement field, ``f'{obj!p:{printer}}'``, whose value is called
    without first being converted to a string.  Any other spec is a :exc:`SyntaxError`.
  * In ``str.format()``, a format spec after ``!p`` pads the pretty printed string.
  * T-strings support ``!p``.  :class:`~string.templatelib.Interpolation` gets a ``printer`` attribute,
    and :func:`string.templatelib.convert` handles ``'p'``.
  * Describe compatibility with Rich, IPython and other pretty printing protocols.
  * Move the Rationale section after the Specification, as :pep:`12` now recommends.

* `04-Mar-2026 <https://discuss.python.org/t/pep-813-the-pretty-print-protocol/106242/79>`__

  * For f-strings only (not ``str.format()``) the ``!p`` conversion specifier takes an optional "format spec".
  * The PEP no longer proposes a ``pretty`` argument to the ``print()`` built-in function.  With the
    addition of ``!p:callable`` syntax for f-strings, the new argument is unnecessary.
  * Specify that to pretty print tuples as positional arguments, use the 2-tuple value format, passing
    a "false-y" value as the argument name.
  * Clarify that a truth-y ``name`` must be a ``str``.
  * Specify that the ``!p`` conversion in f-strings and ``str.format()`` implicitly perform an
    import of the ``pprint`` module.
  * Describe the new Limited C API function ``PyObject_Pretty()``, and add the optional argument.

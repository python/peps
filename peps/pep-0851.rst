Abstract
========

Add ``list.discard(x)``, which removes the first item equal to *x* if one
is present and does nothing otherwise, returning whether an item was
removed. It is the non-raising counterpart to :meth:`list.remove`, which
currently has none. The name is taken from :meth:`set.discard`, which
already means "remove if present" in Python.


Motivation
==========

Removing a value that may not be present is `usually written as
<https://stackoverflow.com/questions/4915920/how-to-delete-an-item-in-a-list-if-it-exists>`__::

    if x in lst:
        lst.remove(x)

or::

    try:
        lst.remove(x)
    except ValueError:
        pass

The first form is clear but scans the list twice on a hit, and if the list
is shared between threads another thread can remove the item between the
two calls, turning a no-op into a :exc:`ValueError`. The second avoids both
problems but obscures the intent. It is four lines for one operation, pays
for raising and catching an exception on every miss, and
``except ValueError`` is broad enough to hide unrelated errors from a
user-defined :meth:`~object.__eq__`.

Both are common. A search of the 5,000 most downloaded PyPI projects [#search]_
finds 1,062 matches for the first form across 411 projects and 331 for
the second across 164 projects. Some of these are on other container
types; in the standard library, excluding tests, two of the 29 matches are
on deques and the remaining seven and 20 are on lists, for example in
`logging
<https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/logging/__init__.py#L840-L841>`__,
`warnings <https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/_py_warnings.py#L326-L329>`__,
`tkinter <https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/tkinter/__init__.py#L490-L493>`__,
`runpy <https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/runpy.py#L312-L315>`__ and
`asyncio <https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/asyncio/subprocess.py#L100-L101>`__.
Each becomes a single call that states the intent directly::

    lst.discard(x)

The cost of providing this is small, as ``discard()`` reuses the existing
search and removal implementation of :meth:`remove() <list.remove>`.


Specification
=============

``list`` gains a positional-only method ``discard(value, /)``. It removes
the first item equal to *value* and returns ``True``, or returns ``False``
if there is no such item. Only the absence of a matching item is reported
by the return value; any other error, including a :exc:`ValueError` raised
during equality comparison, propagates as an exception. The implementation
shares the search loop of :meth:`remove() <list.remove>`, so which item is
removed, how values are compared and the thread-safety properties are
identical to ``remove()``. :class:`collections.UserList` gains the same
method for consistency.


Rationale
=========

Symmetry with :class:`set` is not the goal. The motivation is the missing
non-raising form of :meth:`list.remove`. :class:`set` only supplies the name,
since :meth:`set.discard` already means "remove if present" in Python.

It has been raised that after ``s.discard(x)`` the test ``x not in s``
holds, while after ``lst.discard(x)`` it need not if *x* appears more than
once. That is a property of sets, not of ``discard()``, and
:meth:`list.remove` has the same behaviour today. ``discard()`` follows
``remove()`` here, and its will documentation clearly say so.

Unlike :meth:`set.discard`, which returns ``None``, a bool is returned. This
costs nothing, since the implementation already knows the outcome, and lets
``if lst.discard(x):`` replace the double scan for callers who care.


Backwards Compatibility
=======================

:class:`list` subclasses defining their own ``discard`` keep it. Code using
``hasattr(obj, "discard")`` to tell sets from lists would be affected.
None was found in the standard library or the top 5,000 PyPI packages.


Security Implications
=====================

None.


How to Teach This
=================

Introduce it in the `tutorial
<https://docs.python.org/3/tutorial/datastructures.html#more-on-lists>`__
directly after :meth:`list.remove`, with ``remove()`` for when the item
must be present and ``discard()`` for when it may not be. The same pairing
already exists for :class:`set`.


Reference Implementation
========================

A reference implementation can be found in `python/cpython#160726

Rejected Ideas
==============

A parameter on ``remove()``
---------------------------

A separate method is preferred over a parameter such as
``remove(x, missing_ok=True)``. The standard library has precedent for both
shapes, :meth:`Path.unlink(missing_ok=True) <pathlib.Path.unlink>` and
:func:`os.makedirs(exist_ok=True) <os.makedirs>` on one side and
:meth:`set.remove` / :meth:`set.discard` on the other, but the closest
precedent is ``set``, and following it means the two container types share
one vocabulary. A method also reads more clearly at the call site, since
``lst.discard(x)`` says what happens while a flag describes what does not.

Adding ``discard()`` to ``collections.abc.MutableSequence``
-----------------------------------------------------------

:class:`collections.abc.MutableSequence` is left unchanged, as is the case
for :meth:`list.copy`. Adding ``discard()`` to the ABC would change the
interface of every third-party subclass, while virtual subclasses
registered with ``register()`` would not gain it at all.

``deque.discard()``
-------------------

The `original discussion
<https://discuss.python.org/t/add-list-discard-and-deque-discard/104330>`__
also proposed :class:`collections.deque` gaining the same method. It is
left out of this PEP to keep the proposal to the builtin :class:`list`.
It can follow as a routine change if this PEP is accepted.

PEP: 851
Title: Add list.discard()
Author: Stan Ulbrych <stan@python.org>
Discussions-To: Pending
Status: Draft
Type: Standards Track
Created: 26-Oct-2026
Python-Version: 3.16
Post-History: `12-Oct-2025 <https://discuss.python.org/t/add-list-discard-and-deque-discard/104330>`__


Abstract
========

Add ``list.discard(x)``, which removes the first item equal to *x* if one
is present and does nothing otherwise, returning whether an item was
removed. It is the non-raising counterpart to ``list.remove()``, as
``set.discard()`` is to ``set.remove()``.


Motivation
==========

Removing a value that may not be present is currently `usually written as
<https://stackoverflow.com/questions/4915920/how-to-delete-an-item-in-a-list-if-it-exists>`__::

    if x in lst:
        lst.remove(x)

or::

    try:
        lst.remove(x)
    except ValueError:
        pass

The first form is clear but scans the list twice on a hit, and if the list
is shared between threads another thread can remove the item between the
two calls, turning a no-op into a ``ValueError``. The second avoids both
problems but obscures the intent. It is four lines for one operation, pays
for raising and catching an exception on every miss, and
``except ValueError`` is broad enough to hide unrelated errors from a
user-defined ``__eq__``.

Both are common. A search of the 5,000 most downloaded PyPI projects [#search]_
finds 1,062 matches for the first form across 411 projects and 331 for
the second across 164 projects (a small fraction of these will be on other
container types). Excluding tests, the standard library contains
7 and 20 respectively on lists, for example in `logging
<https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/logging/__init__.py#L840-L841>`__,
`warnings <https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/_py_warnings.py#L326-L329>`__,
`tkinter <https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/tkinter/__init__.py#L490-L493>`__,
`runpy <https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/runpy.py#L312-L315>`__ and
`asyncio <https://github.com/python/cpython/blob/3acc941f2b7288b212a4163ab21aa79faff9cd13/Lib/asyncio/subprocess.py#L100-L101>`__.
Each becomes a single call that states the intent directly::

    lst.discard(x)

The cost of providing this is small, as ``discard()`` reuses the existing
search and removal implementation of ``remove()``.


Specification
=============

``list`` gains a positional-only method ``discard(value, /)``. It removes
the first item equal to *value* and returns ``True``, or returns ``False``
if there is no such item. Only the absence of a matching item is reported
by the return value; any other error, including a ``ValueError`` raised
during equality comparison, propagates as an exception. The implementation
shares the search loop of ``remove()``, so which item is removed, how
values are compared and the thread-safety properties are identical to
``remove()``. ``collections.UserList`` gains the same method for consistency.


Rationale
=========

The name follows the ``remove()`` / ``discard()`` distinction already
made by ``set``, where ``discard()`` is the variant that tolerates a
missing item. It has been raised that ``s.discard(x)`` guarantees
``x not in s`` afterwards, while ``lst.discard(x)`` does not if *x*
appears more than once. This is a real difference. ``discard()``
deliberately shares the search and removal semantics of ``list.remove()``
rather than those of ``set.discard()``, and the documentation states this
explicitly. The name remains the least surprising choice as users who know
sets can apply that knowledge directly.

Unlike ``set.discard()``, which returns ``None``, a bool is returned
(thanks to Guido van Rossum for the suggestion). This costs nothing, since
the implementation already knows the outcome, and lets
``if lst.discard(x):`` replace the double scan for callers who care.

``deque.discard()`` is a possible follow-up if this PEP is accepted.


Backwards Compatibility
=======================

``list`` subclasses defining their own ``discard`` keep it. Code using
``hasattr(obj, "discard")`` to tell sets from lists would be affected.
None was found in the standard library or the top 5,000 PyPI packages.


How to Teach This
=================

Introduce it in the tutorial directly after ``remove()``, with ``remove()``
for when the item must be present and ``discard()`` for when it may not
be. The same pairing already exists for sets.


Reference Implementation
========================

A reference implementation can be found in `python/cpython#160726
<https://github.com/python/cpython/pull/160726>`__.


Rejected Ideas
==============

A parameter on ``remove()``
---------------------------

A separate method is preferred over a parameter such as
``remove(x, missing_ok=True)``. The standard library has precedent for both
shapes, ``Path.unlink(missing_ok=True)`` and ``os.makedirs(exist_ok=True)``
on one side and ``set.remove()`` / ``set.discard()`` on the other, but the
closest precedent is ``set``, and following it means the two container
types share one vocabulary. A method also reads clearer at the call site,
since ``lst.discard(x)`` says what happens while a flag describes what
does not.

Adding ``discard()`` to ``collections.abc.MutableSequence``
-----------------------------------------------------------

``collections.abc.MutableSequence`` is left unchanged, as is the case for
``list.copy()``. Adding ``discard()`` to the ABC would change the interface
of every third-party subclass, while virtual subclasses registered with
``register()`` would not gain it at all.
